# Ticket audit — #2 through #10

Audited 2026-08-04 against the stated core goal:

> train a model on a **120-day input feature tensor** to predict **10-day future log returns**

Sources checked: GitHub issues #2–#10 (bodies + resolution comments), `kb/*.md`, `kb/*.json`,
`prdict/*.py`, `scripts/*.py`, and the merged git history on `main` (`5a86464`).

---

## Summary

**Not aligned. The output half is right; the input half is wrong.**

| Half of the goal | Verdict |
|---|---|
| Predict **10-day future log returns** | ✅ **Aligned.** Settled in map decision 2, confirmed by #6, specified exactly by #8 as one `(n, 10)` array of `log(C_{i+k}/C_{i+k-1})`, k=1..10. Nothing in #2–#10 contradicts it. |
| **120-day input feature tensor** | ❌ **Not aligned.** The entire chain is built on a **60**-session input window. The number `120` does not appear anywhere in the tickets, the specs, or the code. |

The divergence is not a drafting slip in one ticket. It was fixed in the **charting session, before any
ticket existed**, as map decision 1, and then inherited as a settled constant by #3, #4, #5, #8, #10 and
by `scripts/build_trading_calendar.py`. Every downstream number that touches the window — first usable
origin, trainable-origin count, fold boundaries, row-level separation distance, TFT epoch cost — was
derived from 60.

A second, independent divergence sits beside it: the window carries a **30-session future block** even
though the target is only **10** steps long. Under a "120 in / 10 out" statement of the goal, both the
60 and the 30 are wrong.

**Cost of realignment: moderate, and concentrated.** The feature-side tickets (#3, #7, #9) are
window-agnostic — the 280-column encoding contract is unaffected. The calendar, target, and fold specs
are all *generated by scripts from named constants*, so the fix is a constant change plus a rebuild, not
a rewrite. See "Suggested fix" per item below.

## Per-ticket findings

### #2 — Map: astro-feature pipeline to three-model comparison (OPEN)

The map is the origin of the divergence, not a victim of it.

- **Decision 1** states the window as `"60 past / 30 future / 10 ahead"` and marks it settled.
- **Decision 9** describes PCA as preserving "the **90-step** time axis" — 90 = 60 + 30, so the window
  constant is baked into a second, unrelated decision.
- Decision 2 (10-step target vector), decision 5 (drop all price-derived features), decision 7
  (two-stage selection) and decision 8 (trading-simulation scoring) are all consistent with the goal
  and with each other.
- Housekeeping defect: the "Decisions so far" entry for #10 cites **PR #34**, which is still **open**.
  The map therefore describes a spec that is not in the repository. See Divergence 3.

### #3 — Column inventory and type classification (CLOSED)

Sound, and **window-agnostic** — it classifies columns, not timesteps. Two window references leak in:

- `kb/column_spec.md:260`: *"the past-60 and future-30 blocks carry an identical feature set, so the
  **90-step** window is simply contiguous"*.
- The *conclusion* of that sentence survives any window length — every feature is known-future, so the
  window is contiguous whatever its size. Only the literals `60`, `30`, `90` are wrong.

No conflict with any other ticket. The 215 → 207 → 206 feature-count revisions from #30 and #7 are
tracked consistently in both the map and `kb/column_spec.md`.

### #4 — Forward trading-day calendar (CLOSED)

Methodologically the strongest ticket in the set (rule validated against 26 years of history, 0.26%
error, frozen holiday list, byte-reproducible). But its two headline deliverables are **both functions
of the window constants**:

- `PAST = 60`, `FUTURE = 30`, `HORIZON = 10` are hardcoded at `scripts/build_trading_calendar.py:43-47`.
- *"Last usable origin `2026-12-16`, **117 forward origins**"* is computed as "last session with 30
  sessions strictly after it". It is a `FUTURE=30` number, not a `HORIZON=10` number.
- The ticket itself already noticed the tension: *"cutting the decoder to 10 steps would buy 20 more"*
  (117 → 137). It priced the fix and then did not apply it, because #5 had left the decoder length open.

### #5 — Research: TFT stack on CPU (CLOSED)

The pick (`pytorch-forecasting` 1.8.x, v1 API) is unaffected by window length — the library owns
windowing, so changing 60 → 120 is a `max_encoder_length` argument, not a pipeline redesign. That is
good news for the fix.

Two items are window-sensitive and will need re-pricing:

- The measured **145.7 s/epoch** was taken at *"~6500 samples × **90 timesteps** × ~200 features"*.
  A 130-step window is ~1.44× the timesteps, and TFT's interpretable multi-head attention is quadratic
  in encoder length, so the "plan CV as an overnight job" budget is optimistic under 120.
- #5 explicitly left **"10 vs 30 decoder steps"** open. That open question is the direct ancestor of
  Divergence 2 — every downstream ticket then treated 30 as settled anyway.

### #6 — Research: XGBoost native multi-output (CLOSED)

**Fully aligned and no issues found.** Resolves map decision 2's conditional in the direction that
matches the goal: both models take the 10-step vector, `multi_strategy="one_output_per_tree"`,
`xgboost>=3.3.0` as a hard floor. The rejection of the cumulative variant (18.9% of gradient budget to
h10 vs 1.4% to h1) is correct reasoning and keeps a single target definition.

Note for later: XGBoost consumes a **flat** design matrix. A 120-step input window is a real cost here
that a 60-step window did not have — flattening 280 features × 120 steps is 33,600 columns against
16,800. The map has never stated how XGBoost consumes the time axis. This is #11's problem but the
goal statement makes it twice as sharp.

### #7 — Angular columns: periods and sin/cos transform (CLOSED)

**Window-agnostic and internally sound.** Per-row transform, no time axis involved. The `_dist` finding
(values are unwrapped `abs(lon_a − lon_b)`, not angles) and the #30 amendment that keeps the raw
columns are both consistent with the map and with #9's 107-column `linear_numeric` family. Pair
atomicity binds #12/#13 and is correctly propagated into #10's in-fold prune rules.

No divergence from the goal.

### #8 — Target construction (CLOSED)

**The half of the goal that is right.** `(6448, 10)`, `y[k] = log(C_{i+k}/C_{i+k-1})`, no winsorisation,
no normalisation, cumulative derived at read time. Exactly "10-day future log returns".

Its **input**-side numbers inherit the 60:

- *"**First usable origin `2000-03-29`** (the 60th session). The series starts `2000-01-03`; the encoder
  needs 60 sessions up to and including the origin."*
- The `6448` origin count, which then propagates into `(6448, 10)`, `kb/fold_spec.md`, and the map.

It also introduces a covariate that has no home in #9's contract — see Divergence 4.

### #9 — Encoding pipeline: two views from one source (CLOSED, merged)

**Window-agnostic by design and correctly scoped.** It is explicit that it owns semantics and #11 owns
layout, so it never mentions the time axis at all. 280 columns (14 boolean / 67 categorical / 92 cyclic
/ 107 linear numeric), asserted against `angular_spec` on every run.

**A 60 → 120 change does not touch this ticket.** That is the one piece of good structural news in this
audit: the encoding contract is per-row, so re-windowing costs nothing here.

One gap: no home for `elapsed_1..elapsed_10` (Divergence 4).

### #10 — Walk-forward folds, holdout, purge/embargo (CLOSED — but see Divergence 3)

Two versions exist and they disagree with each other.

- **The version in the repo** (`kb/fold_spec.md`, from merged PR #32): expanding window, 5 folds,
  69-session embargo, 3393 validation origins, claims *"100% complete row-level independence"*.
- **The version the map and the closing comment describe** (PR #34, **still open**): rolling window,
  2470 training origins per fold, **no embargo**, purge 10, 3367 concatenated origins, and states the
  69-session embargo *"withheld nothing"* and the independence claim was *"false"*.

Both versions carry window-derived arithmetic. The repo version's embargo derivation reads
*"69 sessions (**60 encoder lookback** + 9 label overlap)"* — the single place the fold spec touches the
input window, and it is wrong twice over under a 120-day input.

## Divergences

### D1 — The input window is 60 sessions, not 120 · **#2, inherited by #3, #4, #5, #8, #10**

**The decision that caused it — map #2, "Settled while charting", decision 1:**

> | 1 | **Trading days only.** **"60 past / 30 future / 10 ahead"** are *trading* days. Collapse to the 6517 rows where the market was open. |

**Why it diverges.** The goal names a **120-day input feature tensor**. Every artifact in the repo
encodes 60:

| Location | Text |
|---|---|
| `scripts/build_trading_calendar.py:43-45` | `# Window arithmetic from map decision 1 — 60 past / 30 future / 10 ahead` / `PAST = 60` |
| `kb/trading_calendar.json` | `"index": {"n_sessions": 6663, "past": 60, "future": 30, "horizon": 10}` |
| `kb/trading_calendar.md:50` | "An **origin** is the last trading day of the **past-60** encoder block." |
| `kb/target_spec.md:29` | "**`2000-03-29`** — 60th session… the encoder needs **60** sessions up to and including the origin." |
| `kb/column_spec.md:260` | "the **past-60** and future-30 blocks… the **90-step** window is simply contiguous" |
| `kb/fold_spec.md:33` | "69 sessions (**60 encoder lookback** + 9 label overlap)" |
| `kb/encoding_spec.md` | *(clean — window-agnostic)* |

**Measured consequences of moving 60 → 120** (computed against `nft50.csv`'s 6517 observed sessions):

| Quantity | At `PAST=60` | At `PAST=120` |
|---|---|---|
| First usable origin | `2000-03-29` | **`2000-06-26`** |
| Trainable origins | **6448** | **6388** (−60) |
| Last trainable origin | `2026-06-15` | `2026-06-15` (unchanged — bound by `HORIZON`) |
| Target array shape | `(6448, 10)` | `(6388, 10)` |
| Window depth for PCA/time axis | 90 steps | 130 steps (or 130 → see D2) |
| Row-level separation cost | 69 sessions | 129 sessions |
| TFT epoch time (measured 145.7 s at 90 steps) | 145.7 s | **≥ ~210 s**, superlinear — attention is quadratic in encoder length |

**⚠️ One thing to confirm before applying the fix:** map decision 1 rules that window units are
**trading** days. "120-day" in the goal statement is ambiguous:

- **120 trading days** ≈ 5.7 calendar months → the table above applies as written.
- **120 calendar days** ≈ **82 trading days** → first usable origin ≈ `2000-05-02`, ~6426 trainable
  origins.

The rest of this document assumes **120 trading days**, consistent with decision 1. If calendar days
were meant, decision 1 itself needs amending, not just the constant.

**Suggested fix.**

1. Amend map #2 decision 1 to read **"120 past / 10 future / 10 ahead"** are trading days, with a
   struck-through `~~60 past / 30 future~~` and a one-line note that the amendment came from the stated
   modelling goal, not from new evidence. (This is the same amendment convention decisions 2 and 6
   already use.)
2. Amend map #2 decision 9: "preserves the **90-step**" → **130-step** time axis.
3. `scripts/build_trading_calendar.py`: `PAST = 60` → `PAST = 120`. Update the comment on line 43.
   Rerun `./container/run.sh python scripts/build_trading_calendar.py`.
4. Rerun `scripts/build_column_spec.py` (the 90-step sentence is generated at
   `scripts/build_column_spec.py:390-391`, so it corrects itself).
5. Reopen **#8** for a numbers-only amendment: first usable origin `2000-06-26`, `(6388, 10)`. The
   *definition* is untouched; only the origin range moves. Rerun `prdict/targets.py`'s self-check.
6. Reopen **#10** — the fold arithmetic `5847 CV origins = 2470 train + 10 purge + 5 × 673 val + 2` is
   derived from the trainable-origin count and must be rebuilt from 6388. Do this **after** D3 is
   resolved, on top of PR #34, not on top of the version in `main`.
7. Reopen **#5**'s CPU-budget line only: re-measure s/epoch at 130 timesteps before committing to
   "overnight job". No part of the stack decision changes.
8. **No change to #3, #7, #9.** Verified window-agnostic.

### D2 — The future block is 30 sessions but the prediction horizon is 10 · **#2, #4, #5, #10**

**The decision that caused it — map #2, decision 1 again, and its consequence in #4:**

> `kb/trading_calendar.md:55` — "**Last origin with a full future-30 block** | **`2026-12-16`**"
>
> `kb/trading_calendar.md:59` — "Forward inference therefore covers **117 origins**… Origins between
> there and `2027-01-14` are reachable **only if the decoder is shortened to 10 steps** — an open
> question in #5."

**Why it diverges.** The goal says predict **10-day** returns. #8 and #6 both fix the target at exactly
10 steps. But the window still reserves **30** future sessions of known covariates, and every origin
must have 30 sessions after it to be usable. Twenty sessions of that block are decoded into nothing.

This is not free. It is currently costing three separate things:

| Cost | Where | Magnitude |
|---|---|---|
| Lost forward inference runway | `kb/trading_calendar.md:55-59`, map #4 entry | **117 origins instead of 137** — 20 origins, already priced by #4 and never collected |
| Purge residual in the folds | #10 resolution, §3 | *"Each training block's **30-session known-future block** still reaches **21 sessions** into its validation dates."* At `FUTURE=10` this collapses to **1 session** |
| Decoder compute | #5 | TFT decodes 30 steps to score 10 |

The 21-session residual is worth emphasising: #10 accepted it on the grounds that "every feature is
known-future (#3)", which is a valid argument — but it is an argument for tolerating a leak surface that
**a 10-step decoder would not create in the first place**.

**Suggested fix.**

1. `scripts/build_trading_calendar.py:46`: `FUTURE = 30` → `FUTURE = 10`, making `FUTURE == HORIZON`.
   Add a comment stating they are now the same quantity by decision, so a future reader does not
   re-split them.
2. Amend map #2 decision 1 as in D1 step 1 (same edit covers both).
3. Close #5's open sub-question **"10 vs 30 decoder steps"** in favour of **10**, with the reason
   recorded: the target is 10 steps, so decoding 30 buys nothing and costs 20 forward origins plus a
   21-session in-fold residual. Strike it through in the map's "Model training plans" bullet, the same
   way the `scalers=` sub-question was struck when #9 answered it.
4. Rebuild the calendar; the runway becomes `last_origin_horizon_only` (`2027-01-14`) and **137 forward
   origins**. Update the map's #4 entry and the "Forward inference run" bullet, which currently says
   *"the 117 origins #4 fixed"*.
5. Rebuild the fold spec — the 21-session residual paragraph in #10 becomes a 1-session residual and
   should be restated, not deleted.

### D3 — #10's resolution is not in the repository · **#10, PR #34**

**The problem.** Issue #10 is **CLOSED**. Its resolving PR **#34 is OPEN**. `main` therefore carries
the *superseded* spec from PR #32, and the map's "Decisions so far" entry describes a document that
does not exist on disk.

The two versions contradict each other on load-bearing points:

| Point | `kb/fold_spec.md` on `main` (PR #32) | #10's closing comment / map (PR #34) |
|---|---|---|
| Geometry | **"Expanding Window (Anchored Walk-Forward)"** | **"rolling, not expanding"** |
| Train size | 2445 → 5157 origins, growing | **2470 origins, fixed, every fold** |
| Embargo | **"69 sessions… for 100% complete row-level independence"** | **"No embargo."** and *"the previous 69-session embargo **withheld nothing**"*, *"its '100% row-level independence' was **false**"* |

**Suggested fix.**

2. After merging, re-verify that `kb/fold_spec.md` no longer contains the string `69 sessions` or

3. Process note worth adopting: **do not close a ticket while its resolving PR is open.** This is the
   second occurrence — #30 had the same shape earlier. A ticket is resolved when the spec is on `main`,
   not when the comment is posted.

### D4 — `elapsed_1..elapsed_10` has no home in the encoding contract · **#8 vs #9**

**The decision that caused it — #8, `kb/target_spec.md:66`:**

> **"Consequence for the feature tickets.** `elapsed_days` is a decoder-side known-future covariate: a
> real column for the TFT's `time_varying_known_reals`, and **10 columns for XGBoost's flat design
> matrix**. It is calendar-derived, not price-derived, so map decision 5 does not touch it."

**Why it diverges.** #8 declares a new input covariate and explicitly hands it to "the feature tickets".
#9 then specifies the complete input contract as **exactly 280 columns**, asserted against
`angular_spec.model_input_width` on every build — and never mentions `elapsed` anywhere. `grep -rn
"elapsed" kb/ prdict/ scripts/` returns hits only in `kb/target_spec.md` and `prdict/targets.py`.

So a real, decided input feature exists in one spec and is structurally rejected by another: adding it
to the encoded frame would trip #9's width assertion.

This is not fatal — `elapsed` is arguably layout (#11's territory, which #9 explicitly disclaims) and
it is target-block-aligned rather than window-aligned. But nothing says so, and it will surface as a
build failure in #11 rather than as a decision.

**Note:** this covariate is **10 columns because the horizon is 10**, so it is unaffected by D1 and is
one of the few things D2 would *not* change either.

**Suggested fix.** One paragraph in `kb/encoding_spec.md` (generated — so add it in
`scripts/build_encoding_spec.py`'s markdown writer, not by hand), stating:

> `elapsed_1..elapsed_10` (#8) is a **decoder-side known-future covariate, not a member of the 280-column
> feature block.** Fit scope `none` — it is read directly from the trading-day index. Its placement in
> the emitted frame is #11's, and the 280-column assertion here deliberately does not count it.

Then add a matching cross-reference line to `kb/target_spec.md`'s "Consequence for the feature tickets"
paragraph naming #11 as the owner, so the handoff is explicit rather than implied.

### D5 — Minor: XGBoost's consumption of the time axis is unspecified, and 120 doubles its cost · **#6, #11**

Not a contradiction, but a divergence the goal statement creates. #6 settled that XGBoost takes a
10-element output vector natively. It never settled how a **sequence** input reaches a tree model.

At 60 steps × 280 features a flattened design matrix is 16,800 columns. At 120 steps it is **33,600
columns** against 6,388 rows — a 5:1 feature-to-sample ratio, before set 1 / set 2 selection.

**Suggested fix.** Not a #2–#10 edit. Add an explicit sub-question to **#11**: *"how does XGBoost
consume the 120-step input — full flatten, a strided/decimated subset of lags, or aggregate statistics
per feature over the window?"* Flag in the map's "Not yet specified → Model training plans" bullet that
the 120-step window makes this a first-order question rather than a detail.

## #9 / #10 sync check

**Verdict: the two tickets' *resolutions* agree. The conflict is between #9 and the fold spec that is
currently on `main`, and it disappears when PR #34 merges.**

### Where they agree (verified)

| Point | #9 says | #10 (PR #34 version) says |
|---|---|---|
| Scaler fit scope | `linear_numeric` → **fit scope `fold`**, `build_fold()` requires `train_idx`, `FoldState` refuses to pickle | *"Inside every fold, on the inner training block only: **scaler**, correlation prune, MI/Spearman ranking, PCA(0.95)"* |
| Categorical encoders | **fit scope `global`** — "fitted once on declared metadata, never on observed values" | *"Once, globally — and why that cannot leak: … **the declared categorical level list** (map decision 6, which makes encoding fold-invariant by construction)"* |
| sin/cos transform | `cyclic` → **fit scope `none`**, "deterministic; no parameters, no leak surface" | *"and the sin/cos transform (#7, parameter-free)"* — listed under global/structural |
| Constant columns | out of scope (dropped upstream by #3) | *"the 28 constant columns (#3, constant **by definition**, so they carry no fold-specific information)"* |
| Pair atomicity | cyclic pairs pass through **unscaled** — "standardising the halves separately breaks `sin²+cos²=1`" | *"the prune and ranking treat each pair as one indivisible unit"* |

The two documents were written independently and land on the same three-way split — deterministic /
global-structural / fold-empirical. #10's "structural versus empirical" is #9's `none`+`global` versus
`fold`, under different names. **This is genuine agreement, not coincidence.**

### Where they conflict

**C1 — #9's `global` scope vs the fold spec on `main`.** `kb/fold_spec.md` §4 (PR #32 version) lists
in-fold fits as a single flat table ending with *"Data-Dependent Redundancy / Variance Filter — any
empirical zero-variance or empirical redundancy filtering evaluated strictly inside each training
fold"*, with **no** carve-out for structural/global fits. Read literally against #9, a reader must
decide whether the declared categorical level list is "data-dependent redundancy" and therefore
fold-scoped — which #9 forbids by construction (`load_global()` has no parameter fold data could arrive
through).

*Fix:* merge PR #34. Its "structural versus empirical" section states the carve-out explicitly and
names the level list under global. **No edit to #9 needed.**

**C2 — Different vocabulary for the same taxonomy.** #9 says `none` / `global` / `fold`. #10 says
"structural" / "empirical". Both are correct; neither references the other's terms.

*Fix:* one sentence in `kb/fold_spec.md` §4 (add to `scripts/build_fold_spec.py`'s writer):
*"These map onto #9's fit scopes: structural = `none` + `global`, empirical = `fold`. `prdict/encoding.py::assert_fit_boundary()`
enforces the encoding-stage half of this split at import time."*

**C3 — Nothing wires the two modules together.** `prdict/folds.py` emits `FoldSplit` objects with
`train_origins`. `prdict/encoding.py` exposes `build_fold(spec, frame, train_idx)`. Neither module
imports the other, and no spec states that `FoldSplit.train_origins` is the intended `train_idx`. The
enforcement #9 built is real but currently unconnected to the thing it is meant to constrain.

*Fix:* #11 (which owns assembly) should be given an explicit acceptance criterion: *"the fold loop calls
`encoding.build_fold(spec, frame, split.train_origins)` and `assert_fit_boundary()` runs once at
pipeline start."* Add it as a bullet to #11's body.

**C4 — Scope-completeness is unstated.** #9's `assert_fit_boundary()` asserts *"exactly one fold-scoped
family"*, which is true of the **encoding stage** but false of the pipeline — #10 puts prune, ranking
and PCA inside folds too. Nothing in #9 says the assertion is scoped to encoding only, so a reader of
`prdict/encoding.py` alone could conclude the scaler is the pipeline's only in-fold fit.

*Fix:* one clause in `prdict/encoding.py`'s `assert_fit_boundary()` docstring and in
`kb/encoding_spec.md`'s "Fit scope is the whole point" section: *"'exactly one fold-scoped family' is a
statement about the **encoding** families only. #10 fits the correlation prune, MI/Spearman ranking and
PCA inside folds as well; those are #12/#13 stages downstream of this contract."*

### Window sync between #9 and #10

**#9 is window-free and therefore cannot conflict with #10 on D1 or D2.** The only window number in
either document is `kb/fold_spec.md:33`'s *"60 encoder lookback"* — which is in the superseded version,
is deleted by PR #34 (which drops the embargo entirely), and is wrong under a 120-day input anyway.
After merging PR #34, **neither spec contains a window constant**, and the D1/D2 fixes touch only
`scripts/build_trading_calendar.py` and the specs generated from it.
